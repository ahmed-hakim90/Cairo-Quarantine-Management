# عرض سعر مبدئي
## تطوير منصة إدارة الحجر الصحي - مرحلة Single VPS + Docker + PostgreSQL + Redis + Vercel

**التاريخ:** 18 مايو 2026  
**العميل:** جهة حكومية / مؤسسة عامة  
**المشروع:** تطوير وتشغيل منصة إدارة الحجر الصحي لتعمل على نطاق المحافظات  
**العملة:** جنيه مصري  
**حالة العرض:** مبدئي، قابل للتحديث بعد مرحلة تحليل المتطلبات واعتماد نطاق العمل النهائي

---

## 1. الملخص التنفيذي

يهدف هذا العرض إلى تنفيذ مرحلة تطوير أولى قوية ومنخفضة التكلفة نسبياً تعتمد على:

- تشغيل واجهة المستخدم Next.js على Vercel.
- تشغيل الخدمات الخلفية على VPS واحد باستخدام Docker.
- استخدام PostgreSQL كمصدر الحقيقة للبيانات الحرجة.
- استخدام Redis للـ cache، rate limiting، idempotency، وحالة الطابور اللحظية.
- تجهيز تصميم قابل للتوسع لاحقاً إلى Managed PostgreSQL/Redis أو أكثر من VPS دون إعادة كتابة كبيرة.

هذه المرحلة مناسبة كبداية إنتاجية عملية، لكنها ليست High Availability حقيقية. في حالة توقف الـ VPS قد يتوقف النظام التشغيلي حتى تتم استعادته.

## 2. نطاق العمل الأساسي

### 2.1 Backend API

يشمل تنفيذ أو استكمال خدمة API مستقلة داخل Docker لإدارة العمليات الحرجة، وتشمل:

- إنشاء طلبات الحجز.
- التحقق من السعة اليومية للمكاتب.
- منع تكرار الحجز أو تكرار الإرسال عند إعادة المحاولة.
- تسجيل الحضور check-in.
- إدارة حالة الطابور.
- إغلاق أو إكمال أرقام الطابور.
- واجهات الإدارة الأساسية للطلبات والمكاتب والإحصاءات.
- تسجيل activity logs للعمليات المهمة.

### 2.2 PostgreSQL

يشمل تصميم وتجهيز قاعدة بيانات PostgreSQL للبيانات التشغيلية الحرجة، ومنها:

- `requests`
- `offices`
- `traveler_states`
- `booking_capacity`
- `queue_tickets`
- `daily_queue_stats`
- `admin_users`
- `activity_logs`

سيتم تنفيذ العمليات الحساسة داخل SQL transactions مع استخدام row locking عند الحاجة لمنع overbooking أو تكرار أرقام الطابور.

### 2.3 Redis

يشمل استخدام Redis في:

- Distributed rate limiting.
- Cache للقوائم المرجعية مثل المكاتب والحالات واللقاحات.
- Queue live state لتقليل الضغط على PostgreSQL.
- Idempotency keys لمنع تكرار العمليات أثناء retry.

Redis لا يعتبر مصدر الحقيقة النهائي. في حالة فقدانه يمكن إعادة بناء الحالة من PostgreSQL.

### 2.4 Docker وVPS

يشمل تجهيز Docker Compose للخدمات التالية:

- `api`
- `worker`
- `postgres`
- `redis`
- `caddy` أو `nginx`

مع إعداد:

- شبكة داخلية بين الخدمات.
- Volumes للبيانات.
- Healthchecks للخدمات.
- Reverse proxy للنطاقات.
- إعدادات البيئة والأسرار.

### 2.5 ربط Vercel بالـ API

يشمل:

- ربط واجهة Next.js بالـ API الجديد.
- ضبط متغيرات البيئة مثل:
  - `NEXT_PUBLIC_API_BASE_URL`
  - `CQM_API_URL`
  - `ADMIN_API_SECRET`
- تحويل العمليات الحرجة من منطق الواجهة أو Server Actions إلى API مستقل عند الحاجة.

### 2.6 Backup وRecovery

يشمل:

- Backup يومي لقاعدة PostgreSQL.
- الاحتفاظ بنسخ لمدة 7 إلى 14 يوم.
- رفع النسخ إلى storage خارجي يتم الاتفاق عليه.
- تجربة restore أولية أثناء التسليم.
- توثيق خطوات الاستعادة.

### 2.7 الاختبارات

يشمل تنفيذ اختبارات أساسية على:

- إنشاء حجز ناجح.
- منع overbooking.
- منع duplicate booking.
- تسجيل حضور لطلب موجود.
- منع duplicate queue ticket.
- إغلاق أو إكمال ticket بدون تكرار الإحصاءات.
- Restart لخدمة API أثناء الإرسال.
- Restart لـ Redis والتأكد من استعادة الحالة من PostgreSQL.
- اختبار ضغط مبدئي حسب الإمكانيات المتاحة في بيئة الاختبار.

## 3. واجهات API المتوقعة

تشمل المرحلة الأساسية واجهات مشابهة للتالي:

| Method | Endpoint | الوصف |
|---|---|---|
| `POST` | `/v1/requests` | إنشاء حجز أو طلب |
| `GET` | `/v1/booking-availability` | التحقق من السعة المتاحة |
| `POST` | `/v1/checkin` | تسجيل حضور |
| `GET` | `/v1/queue/tickets/:ticketId/state` | متابعة حالة رقم الطابور |
| `POST` | `/v1/admin/queue/tickets/:ticketId/complete` | إكمال رقم طابور |
| `GET` | `/v1/admin/requests` | عرض الطلبات للإدارة |
| `PATCH` | `/v1/admin/requests/:id` | تحديث حالة طلب |

قد يتم تعديل المسارات النهائية أثناء التنفيذ بما يتوافق مع بنية المشروع الحالية، مع الحفاظ على نفس العقود الوظيفية.

## 11. افتراضات العرض

- العرض مبني على مرحلة Single VPS وليس High Availability.
- PostgreSQL وRedis داخل Docker على نفس VPS في المرحلة الأولى.
- PostgreSQL هو مصدر الحقيقة النهائي للطلبات والطابور.
- Redis يستخدم كـ cache وطبقة مساعدة وليس كمصدر بيانات نهائي.
- واجهة المستخدم الحالية على Vercel ويتم ربطها بالـ API.
- لا يشمل العرض تكاملات خارجية غير مذكورة صراحة.
- لا يشمل العرض بوابات دفع، SMS Gateway، WhatsApp Business API، توقيع رقمي، تكاملات حكومية، أو ربط مع قواعد بيانات خارجية إلا كبنود إضافية.
- لا يشمل العرض شراء السيرفرات أو خدمات الاستضافة أو حسابات النشر.
- أي توسع إلى High Availability أو أكثر من VPS أو Managed Database يتم تسعيره كمرحلة إضافية.
