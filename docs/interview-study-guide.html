2. التقنيات المستخدمة

التقنيةاستخدامها في المشروعنقطة تقولها في الانترفيو
Next.js 16.2.6 Routing، صفحات عامة، لوحة إدارة، API Routes، Server Actions. المشروع يستخدم App Router، وفي النسخة دي params وsearchParams غالباً Promise.
React 19.2.4 Client components، forms، state، effects، useActionState. الفورم يرسل للسيرفر من غير API يدوي في بعض الحالات عن طريق Server Actions.
Firebase Auth تسجيل دخول الإدارة بالبريد وكلمة المرور. العميل يجيب idToken والسيرفر يحوله إلى session cookie آمنة.
Firestore تخزين الطلبات، المكاتب، اللقاحات، المستخدمين، الطابور، الإعدادات. الداتا التشغيلية كلها في Collections واضحة، ومعها indexes للاستعلامات.
Firebase Admin SDK عمليات السيرفر الآمنة: إنشاء طلب، transactions، session، messaging. المواطن لا يكتب مباشرة في Firestore؛ السيرفر هو مصدر الحقيقة.
Tailwind CSS v4 تصميم الواجهة العامة ولوحة الإدارة. الواجهة RTL/LTR وتدعم لغات متعددة.
Vitest اختبارات لمنطق الحجز، الطابور، التصدير، الصلاحيات. المنطق الحرج متغطي باختبارات منفصلة في lib.

السيرفر الذي اعتمدنا عليه

الإجابة المختصرة: اعتمدنا على Next.js Server Runtime كسيرفر التطبيق، ومعاه Firebase كخدمات Backend جاهزة: Firestore للداتا، Firebase Auth لتسجيل الدخول، وFirebase Admin SDK للعمليات السيرفرية الآمنة. يعني لا يوجد Express أو NestJS server منفصل في المشروع.
جزء السيرفرمسؤوليتهلماذا استخدمناه؟
Next.js Server Runtime تشغيل Server Components، Server Actions، وAPI Routes. لأنه مدمج مع المشروع، يقلل الحاجة لسيرفر منفصل، ويسمح بكتابة الواجهة والباك إند في نفس الكودبيز.
Server Actions استقبال فورم الحجز/الشكوى وتشغيل validation وحفظ الطلب. مناسبة للفورم، وتقلل boilerplate مقارنة بعمل endpoint يدوي لكل submit.
API Routes Endpoints مستقلة مثل availability، status refresh، queue position، admin session. مناسبة للعمليات التي يحتاجها العميل عبر fetch أو polling أو تكاملات خارجية.
Firebase Admin SDK قراءة وكتابة Firestore بأمان من السيرفر، إنشاء session cookies، transactions، messaging. لأن العميل لا يجب أن يملك صلاحية إنشاء الطلبات أو تعديل الداتا الحساسة مباشرة.
Firestore قاعدة البيانات الرئيسية للطلبات والمكاتب والمستخدمين والطابور. Managed database سريعة في التطوير، realtime-friendly، وتدعم فهارس وصلاحيات.

كيف تمشي request على السيرفر؟

1
المواطن يرسل الفورمالفورم يستدعي Server Action مثل submitOfficeRequest.
2
Next.js ينفذ الكود على السيرفرالـ Action تعمل validation وrate limit وتقرأ إعدادات الحجز.
3
Firebase Admin يتعامل مع Firestoreينشئ request، يولد رقم الطلب وQR token، ويستخدم transaction عند الحاجة.
4
النتيجة ترجع للواجهةالمستخدم يرى رقم الطلب والـ QR، ويتحفظ الطلب في localStorage.
ليه مش Express؟ لأن Next.js بالفعل يوفر طبقة سيرفر كافية للمشروع: routes، actions، rendering، cookies، redirects، وintegration مع Firebase. إضافة Express كانت هتزود التعقيد بدون احتياج واضح، خصوصاً أن المشروع ليس REST API ضخم منفصل عن الواجهة.

  • النصوص موجودة في ملفات lib/i18n.

5. Feature: حجز موعد تطعيم

1
تحميل البياناتصفحة الحجز تجيب المكاتب النشطة، حالات المسافر، وإعدادات cutoff من Firestore.
2
اختيار حالة المسافرالمكاتب تتفلتر حسب travelerStateId والخدمة التي يقدمها المكتب.
3
اختيار التاريخالحد الأدنى للتاريخ يعتمد على توقيت القاهرة وساعة cutoff.
4
فحص السعةAPI /api/booking/availability يتأكد أن اليوم لم يصل إلى dailyBookingCap.
5
Server ActionsubmitOfficeRequest يعمل validation كامل على السيرفر.
6
إنشاء الطلبcreateOfficeRequest يستخدم transaction لتوليد رقم طلب متسلسل وحفظ request.
7
نتيجة للمواطنيرجع request number وpass token، ويتحفظ في localStorage ويظهر QR.

قواعد الحجز المهمة

  • حجز نفس اليوم مسموح قبل ساعة cutoff، والافتراضي الساعة 14:00 بتوقيت القاهرة.
  • بعد cutoff، أقل تاريخ مسموح هو الغد.
  • التاريخ في الماضي مرفوض.
  • كل مكتب ممكن يكون له dailyBookingCap؛ لو null يبقى غير محدود.
  • المكتب لازم يكون نشط ويخدم حالة المسافر المختارة.
  • يتم منع الحجز المكرر لنفس المكتب والتاريخ وحالة المسافر وبيانات الشخص.
إجابة ذهبية: الواجهة تعمل validation لتحسين التجربة، لكن السيرفر يعيد كل التحقق قبل الحفظ؛ لذلك لا نعتمد على المتصفح كمصدر أمان.

  • التفاصيل إلزامية.

  • complaint: شكوى.

7. Feature: طلباتي

صفحة /my-requests ليست حساب مستخدم. هي تعتمد على localStorage في جهاز المواطن.

1
بعد إنشاء الطلبيحفظ النظام آخر 20 طلب في localStorage.
2
عند التحديثيبعت request id ورقم الهاتف إلى /api/office-requests/status.
3
التحققالسيرفر لا يرجع الحالة إلا لو الهاتف مطابق للهاتف المسجل.
4
النتيجةيرجع الحالة وملاحظات المتابعة، ومعها QR لو token محفوظ على نفس الجهاز.
Tradeoff مهم: localStorage مريح لأنه لا يحتاج حساب، لكنه مرتبط بالجهاز. لو المواطن مسح بيانات المتصفح قد يفقد قائمة الطلبات والـ QR token.

8. لوحة الإدارة

تسجيل الدخول

  1. المستخدم يدخل البريد وكلمة المرور عبر Firebase Auth.
  2. العميل يحصل على idToken.
  3. يرسل token إلى /api/admin/session.
  4. السيرفر يتحقق من token باستخدام Firebase Admin.
  5. السيرفر يقرأ profile من users.
  6. لو profile موجود، ينشئ session cookie آمنة HttpOnly.

9. Feature: الطابور اليومي

الطابور يخدم يوم العمل داخل المكتب. المواطن يمسح QR خاص بالمكتب ويدخل رقم الطلب أو الهاتف.

1
فتح رابط المكتب/ar/checkin?officeId=... يتأكد أن المكتب نشط.
2
بحث عن الطلببالرقم أو الهاتف باستخدام findRequestByNumberOrPhone.
3
إنشاء Ticketلو الطلب صحيح ومكتبه مطابق، ينشئ ticket في today_queue.
4
رقم الدورtransaction تزود lastQueueNumber في daily_stats.
5
متابعة مباشرةالمواطن يرى رقم الدور وعدد المنتظرين قبله عبر polling كل 20 ثانية.
6
إتمام الخدمةالموظف يعمل complete؛ الطلب يتزامن إلى completed.

Quick Request

لو المواطن جاء بدون طلب مسبق، صفحة الحضور تسمح بإنشاء طلب سريع لنفس اليوم ثم تسجيله في الطابور.

إغلاق اليوم

  • عند إغلاق طابور اليوم يحسب النظام totalNoShow = totalCheckedIn - totalCompleted.
  • يتم حذف مستندات today_queue لذلك اليوم والمكتب.
  • تبقى الإحصاءات محفوظة في daily_stats.

10. الأمان والصلاحيات

Firestore Rules

تمنع public write. قراءة وتحديث الطلبات حسب الدور والمكتب فقط.

Admin SDK

العمليات الحساسة تتم من السيرفر وليس من المتصفح.

Rate Limiting

حدود للطلبات العامة مثل الحجز والتحديث والتحقق من السعة.

قيود مهمة

  • إنشاء request من العميل المباشر ممنوع في Firestore rules.
  • موظف المكتب لا يستطيع تعديل officeId أو بيانات المواطن.
  • تحديث موظف المكتب محدود في status وnotes وlastWhatsappAt وupdatedAt.
  • حذف الطلبات للسوبر أدمن فقط.
  • admin APIs تتحقق من origin وreferer وheader خاص ضد الطلبات غير الآمنة.

Rate limits تحفظها

العمليةالحد
إرسال حجز/شكوى10 طلبات كل 10 دقائق لكل IP.
التحقق من السعة60 طلباً في الدقيقة.
تحديث طلباتي30 طلباً في الدقيقة، وحتى 20 طلب في body واحد.
تسجيل جلسة الإدارة20 محاولة كل 10 دقائق.

13. أسئلة انترفيو متوقعة

اشرح المشروع في دقيقة.

بوابة ويب لإدارة خدمات الحجر الصحي بالقاهرة. المواطن يقدر يشوف معلومات، يحجز موعد، يقدم شكوى، يتابع طلبه، ويسجل حضور في الطابور. الإدارة عندها لوحة لمتابعة الطلبات والمكاتب والمستخدمين واللقاحات والإحصاءات. المشروع مبني بـ Next.js وFirebase، والعمليات الحساسة تتم على السيرفر باستخدام Admin SDK.

ليه استخدمت Firebase Admin SDK؟

لأننا لا نريد أن يكتب المواطن مباشرة في Firestore. السيرفر يتحكم في validation والصلاحيات والtransactions وتوليد أرقام الطلبات والـ session cookies.

إزاي بيتم إنشاء رقم الطلب؟

داخل transaction في createOfficeRequest. يتم قراءة counter من settings/request_numbers ثم زيادته وتنسيقه كرقم طلب مثل CQM-000123 وحفظ الطلب.

إزاي تمنع الحجز في يوم ممتلئ؟

كل مكتب له dailyBookingCap. قبل الحفظ يتم عد حجوزات نفس المكتب ونفس التاريخ ونوع booking. لو العدد وصل للحد، السيرفر يرفض الحجز. الواجهة أيضاً تفحص السعة مسبقاً لتحسين التجربة.

إزاي تمنع الحجز المكرر؟

قبل إنشاء الطلب يتم البحث عن طلب بنفس المكتب والتاريخ وحالة المسافر ورقم الهاتف/بيانات الشخص. لو وجد مطابق يرجع رسالة duplicate ويوجه المستخدم إلى صفحة طلباتي.

إزاي QR آمن؟

الرابط لا يعتمد على id فقط، بل يحتوي على token عشوائي. السيرفر يقارن token ويتأكد من expiry قبل عرض البيانات. كمان الصفحة لا تعرض رقم الهاتف.

ليه طلباتي تستخدم localStorage؟

عشان المواطن يتابع بدون إنشاء حساب. لكن عند تحديث الحالة، السيرفر يطلب id ورقم الهاتف ويتأكد من التطابق قبل إرجاع الحالة.

إزاي صلاحيات الإدارة متقسمة؟

كل مستخدم له profile في users يحتوي role وofficeId أو allowedOfficeIds. الاستعلامات على السيرفر تتفلتر حسب الدور، وFirestore rules تفرض حدود القراءة والتحديث.

إزاي الطابور يضمن رقم دور صحيح؟

إنشاء ticket يتم داخل transaction تقرأ daily_stats.lastQueueNumber وتزوده واحد. كده نقلل مشاكل السباق عند تسجيل أكثر من شخص في نفس الوقت.

ما أهم نقطة أمان في المشروع؟

عدم الاعتماد على العميل. كل validation مهم والصلاحيات وإنشاء الداتا تتم على السيرفر، مع Firestore rules تمنع الكتابة العامة المباشرة.

14. هل النظام يتحمل 50 ألف طلب وحضور في اليوم؟

الإجابة الصريحة: Firestore وNext.js يقدروا يخدموا 50 ألف عملية في اليوم من ناحية المبدأ، لكن النسخة الحالية لا يُفضَّل الاعتماد عليها بثقة لهذا الرقم بدون تعديلات في السعة، الطابور، polling، والمراقبة. لو الـ 50 ألف موزعين على اليوم وعلى مكاتب كثيرة فالفرصة أفضل. لو ضغط لحظي عالي على مكتب واحد، لازم تطويرات قبل الإنتاج.

تقييم أجزاء النظام

الجزءالوضع الحاليالحكم عند 50 ألف/يومالتطوير المطلوب
إنشاء الطلبات Server Action + Firestore write + رقم طلب transaction. مقبول غالباً لو الضغط موزع. مراقبة retries، وتقليل أي reads غير لازمة قبل الحفظ.
سعة الحجز اليومية Count query قبل الحفظ. فيه احتمال race condition تحت الضغط. استخدام capacity document لكل مكتب/تاريخ داخل transaction.
رقم الطابور آخر رقم محفوظ في daily_stats ويتم تحديثه transaction. جيد للضغط المتوسط، لكن قد يصبح hot document في الزحام العالي. تقسيم الطوابير حسب مكتب/نافذة زمنية، أو خدمة queue مخصصة، أو strategy تقلل contention.
متابعة الدور للمواطن Polling كل 20 ثانية + aggregation count. أكبر مصدر تكلفة وضغط لو آلاف فاتحين الصفحة. تقليل polling، push notifications، أو currentServingNumber بدل count لكل مستخدم.
Dashboard استعلامات محدودة وpagination في بعض الصفحات. محتاج تحسين للتقارير الكبيرة. Precomputed analytics وdaily aggregates بدل scan مباشر.

أولويات التطوير قبل الاعتماد الكبير

  1. Atomic booking capacity: استبدال count قبل الحفظ بوثيقة سعة يومية داخل transaction.
  2. Queue position optimization: بدل count لكل مستخدم، نخزن currentServingNumber أو lastCompletedQueueNumber ونحسب ahead = queueNumber - currentServingNumber مع تصحيح للحالات الخاصة.
  3. Reduce polling: نخلي polling adaptive: سريع فقط قرب الدور، وبطيء لمن هم بعيدون، مع الاعتماد على notifications.
  4. Precomputed analytics: تحديث إحصاءات يومية عند إنشاء/تحديث الطلب بدلاً من حسابها من requests كل مرة.
  5. Monitoring: إضافة logs/metrics للأخطاء، زمن الاستجابة، عدد Firestore reads/writes، ومعدلات retry.
  6. Load testing: اختبار سيناريو 50 ألف موزع وسيناريو burst على مكتب واحد قبل الإطلاق.
جملة انترفيو قوية: "النظام معماره يسمح بالتوسع، لكن الوصول لـ 50 ألف حضور يومياً يتطلب تحويل بعض العمليات من حساب مباشر وقت الطلب إلى counters وaggregates، وتقليل polling، ومعالجة hot documents في الطابور."

15. أسئلة تكنيكال عميقة

الأسئلة دي هدفها إنك تبين إنك فاهم التصميم الداخلي، مش بس عارف تستخدم Next وFirebase. اقرأ السؤال، حاول تجاوب بصوتك، ثم افتح الإجابة.

Next.js وReact

ليه استخدمت Server Actions في الحجز بدل ما تعمل API route عادي؟

Server Actions مناسبة للفورم لأنها تربط submit مباشرة بمنطق السيرفر وتقلل boilerplate. في المشروع submitOfficeRequest يستقبل FormData ويعمل validation ويحفظ الطلب. لو العملية محتاجة endpoint عام مستقل أو polling زي availability/status، استخدمنا API routes.

إيه الفرق بين Server Component وClient Component هنا؟

Server Component يستخدم لجلب بيانات أولية بأمان من السيرفر، مثل صفحة الحجز التي تجيب المكاتب وحالات المسافر. Client Component يستخدم للتفاعل: state، effects، localStorage، fetch availability، وإظهار toast. مثال: صفحة booking/page.tsx Server، وBookingRequestForm Client.

ليه params وsearchParams بتتعمل await في الصفحات؟

المشروع على Next.js 16، والنسخة دي تغيرت فيها بعض APIs، لذلك الصفحات تتعامل مع params وsearchParams كـ Promise. دي نقطة مهمة لأن المشروع نفسه حاط تعليمات إن Next هنا فيه breaking changes ولازم ترجع للوثائق المحلية.

ليه بعض الصفحات تجيب الداتا على السيرفر بدل useEffect؟

جلب الداتا على السيرفر يحسن أول تحميل، يقلل flicker، ويخفي تفاصيل الوصول للداتا. مثلاً صفحة الحجز تجيب المكاتب وحالات المسافر قبل render، وبعدها الفورم العميل يتعامل مع التفاعل فقط.

ليه استخدمت useActionState في الفورم؟

لأنه يحافظ على نتيجة Server Action داخل React state: نجاح، أخطاء validation، القيم القديمة، وحالة pending. ده مناسب جداً للفورم لأنه يرجع errors على مستوى الحقول ويخلي الواجهة تركز أول حقل فيه خطأ.

Firestore وتصميم الداتا

ليه كل الطلبات في collection واحدة requests بدل collections منفصلة للحجز والشكاوى؟

لأن الثلاثة لهم دورة متابعة مشتركة: مكتب، حالة، اسم، هاتف، ملاحظات، timestamps، ولوحة إدارة واحدة. وجودهم في collection واحدة يسهل الفلاتر والتحليلات والتصدير. الاختلافات محفوظة في type وحقول اختيارية مثل preferredDate.

إزاي بتتعامل مع Firestore composite indexes؟

الاستعلامات التي تجمع where مع orderBy أو أكثر من فلتر تحتاج indexes. المشروع يعرفها في firestore.indexes.json مثل استعلامات الطلبات حسب officeId وstatus وcreatedAt، والطابور حسب officeId وqueueDate وqueueNumber.

ليه رقم الطلب بيتولد من counter في transaction؟

لأننا نريد رقم تسلسلي مفهوم للإدارة والمواطن مثل CQM-000123. transaction تضمن أن طلبين متزامنين لا يأخذان نفس sequence. بدون transaction ممكن يحصل race condition.

هل عد الحجوزات اليومية فيه احتمالية race condition؟

نعم، لو طلبان وصلوا في نفس اللحظة وكان المتبقي مكان واحد، مجرد count قبل insert قد يسمح بتجاوز السعة. الحل الأقوى مستقبلاً هو counter يومي لكل مكتب/تاريخ داخل transaction، أو document reservation مثل booking_day_stats/{officeId_date} يتم increment عليه بشرط ألا يتجاوز cap.

ليه فيه fallback للبيانات الثابتة مثل المكاتب أو اللقاحات؟

الفكرة أن المشروع يقدر يعرض بيانات أو يبدأ محلياً حتى لو Firestore غير مملوء بالكامل، ثم يتحول للبيانات الديناميكية بعد seed. ده يقلل توقف الواجهة العامة في مراحل الإعداد.

إزاي بتتعامل مع بيانات قديمة قبل traveler states الديناميكية؟

الطلب يدعم travelerStateId للحجوزات الجديدة وtravelerCategory للحجوزات القديمة. فيه helper يحدد الحالة الفعالة، وده يحافظ على backward compatibility بدل ما يكسر البيانات القديمة.

Firebase Auth والجلسات

ليه عملت session cookie بدل الاعتماد على Firebase client token فقط؟

session cookie HttpOnly لا يقرأها JavaScript، فتقلل خطر سرقة التوكن من XSS. كمان صفحات الإدارة Server Components تقدر تتحقق من الجلسة على السيرفر وتعمل redirect قبل عرض أي بيانات.

إيه الفرق بين Firebase Auth user وprofile في users؟

Firebase Auth يثبت هوية المستخدم: uid/email/password. أما profile في Firestore يحدد صلاحيات التطبيق: role، officeId، allowedOfficeIds، active، displayName. وجود Auth user وحده لا يكفي لدخول اللوحة.

ليه فيه صفحة pending review؟

لو المستخدم موجود لكن غير مفعل أو لم يتم ربطه بمكتب، لا نسمح له بدخول dashboard. pending review تمنع access ناقص وتوضح أن الحساب يحتاج مراجعة من السوبر أدمن.

Security

لو حد فتح DevTools وحاول يغير officeId أو type في الفورم، إيه اللي يحصل؟

السيرفر يعيد التحقق. يتأكد أن المكتب موجود ونشط، وأن النوع مسموح، وأن المكتب يخدم حالة المسافر، وأن التاريخ والسعة صحيحين. لذلك تعديل HTML في المتصفح لا يكفي لتجاوز القواعد.

إزاي بتحمي public status endpoint؟

endpoint لا يرجع بيانات بمجرد request id. لازم الهاتف يطابق الهاتف المخزن بعد normalizing variants. كمان فيه limit لحجم body وعدد الطلبات وrate limit.

ما الفرق بين authorization في السيرفر وFirestore rules؟

السيرفر يفلتر الاستعلامات حسب session role قبل قراءة الداتا. Firestore rules طبقة دفاع إضافية لو client حاول يقرأ مباشرة باستخدام SDK. وجود الطبقتين أفضل من الاعتماد على واحدة فقط.

ليه admin APIs تحتاج origin/referer وheader خاص؟

لتقليل مخاطر CSRF والطلبات غير المقصودة. حتى لو المتصفح أرسل cookie، endpoint يرفض الطلب لو origin أو referer مختلف أو header الإدارة غير موجود.

هل QR token يعتبر Authentication؟

هو capability token: من يملك الرابط السري يقدر يرى بيانات محدودة للطلب. لذلك الصفحة لا تعرض الهاتف، والtoken له expiry، والمقارنة تتم على السيرفر.

Performance وScalability

إيه أكثر نقطة ممكن تعمل ضغط على Firestore؟

استعلامات dashboard والتصدير وقوائم الطلبات مع فلاتر كثيرة، وعد الحجوزات اليومية، وpolling الطابور. المشروع يخفف ده بالفهارس، pagination، limits، caching لبعض البيانات العامة، وrate limits.

ليه polling كل 20 ثانية في الطابور بدل realtime listener؟

polling أبسط وأسهل في التحكم بالrate limits ومناسب لأن عدد المنتظرين لا يحتاج millisecond realtime. لو الاحتياج زاد، يمكن استخدام Firestore realtime listener أو WebSocket/Server-Sent Events.

إزاي تتعامل مع export كبير؟

لا نسحب كل البيانات مرة واحدة. نستخدم pagination/cursors وحد أقصى للصفوف، ونفلتر حسب صلاحيات المستخدم. المشروع لديه constants للتصدير وحدود مثل SUPER_ADMIN_EXPORT_MAX_ROWS.

لو عدد المكاتب زاد جداً، إيه التحسينات المطلوبة؟

نحتاج search/pagination للمكاتب في الإدارة، caching أقوى للقوائم العامة، وربما denormalized fields لتقليل joins اليدوية، مع مراقبة Firestore reads والتكلفة.

Testing

إيه أكثر أجزاء لازم تختبرها؟

قواعد التاريخ والcutoff، منع التكرار، صلاحيات الإدارة، pagination/filtering، token expiry، queue number logic، وإغلاق الطابور. لأنها أجزاء فيها business rules وقد تؤثر على بيانات حقيقية.

ليه اختبارات كثيرة في lib مش في components؟

لأن منطق المشروع الحرج موجود في helpers والخدمات: validation، analytics، queue logic، access control. اختبار المنطق هناك أسرع وأكثر ثباتاً من اختبار UI فقط.

16. أسئلة مركبة وسيناريوهات

دي أسئلة أصعب شوية. الإجابة الجيدة فيها تبين إنك بتفكر في الداتا، السباق، الصلاحيات، وتجربة المستخدم معاً.

سيناريو: مكتب سعته اليومية 50، والطلب رقم 50 و51 اتبعتوا في نفس الثانية. هل ممكن الاثنين يتقبلوا؟ وإزاي تصلحها؟

في التصميم الحالي فيه فحص count قبل الإنشاء، وده ممكن نظرياً يسمح بسباق لو الطلبين قرأوا نفس العدد قبل الحفظ. الإصلاح الأقوى هو عمل document لكل مكتب/تاريخ مثل booking_capacity/{officeId}_{date} يحتوي used وcap، وداخل transaction نقرأه ونتأكد أن used < cap ثم نعمل increment وننشئ الطلب. كده check والحفظ يبقوا atomic.

سيناريو: موظف مكتب حاول يفتح طلب مكتب آخر عن طريق تغيير URL. ماذا يحدث؟

على مستوى السيرفر، session profile يحتوي role وofficeId. دوال القراءة مثل listRequestsForSession وقراءة التفاصيل يجب أن تتحقق من access. وعلى مستوى Firestore rules، officeUserFor(resource.data.officeId) تمنع قراءة request لا ينتمي لمكتبه. إذن حتى لو غير URL، لا يحصل على الداتا.

سيناريو: مواطن فقد QR لأنه مسح localStorage، لكنه يعرف رقم الطلب والهاتف. إيه المتاح؟

يستطيع متابعة الحالة عبر "طلباتي" لو عنده id والهاتف من خلال endpoint status، لكن QR token نفسه قد لا يكون متاحاً لأن token كان محفوظ على الجهاز بعد الحجز. تحسين مستقبلي: استرجاع آمن للـ pass عبر OTP على الهاتف أو رسالة واتساب رسمية.

سيناريو: Firebase Admin env غير مضبوط في production. ما الأثر؟ وكيف تكتشفه؟

أي عملية تعتمد على Admin SDK مثل إنشاء الطلبات وتسجيل جلسة الإدارة وقراءة Firestore السيرفرية ستفشل أو ترجع بيانات فارغة حسب الدالة. نكتشفه من errors مثل "Firebase Admin environment variables are not configured"، ومن health check أو logs. الحل مراجعة FIREBASE_PROJECT_ID وFIREBASE_CLIENT_EMAIL وFIREBASE_PRIVATE_KEY خصوصاً newline escaping.

سيناريو: الإدارة قالت إن طلبات اليوم مش ظاهرة لبعض موظفين المكاتب. تبدأ debug منين؟

أبدأ من profile المستخدم: هل active true؟ هل role صحيح؟ هل officeId أو allowedOfficeIds مضبوط؟ ثم أفحص filters في URL، نطاق تاريخ الحجز، وFirestore indexes. بعد ذلك أفحص أن الطلب فعلاً يحمل نفس officeId المتوقع وليس office قديم أو inactive.

سيناريو: المستخدم يختار حالة مسافر ثم المكتب يختفي. هل ده bug؟

ليس بالضرورة. الفورم يفلتر المكاتب حسب حالة المسافر. لو المكتب لا يخدم الحالة المختارة، يتم تفريغ الاختيار وإظهار المكاتب المطابقة فقط. ده يحمي المستخدم من إنشاء طلب لمكتب غير مناسب.

سيناريو: طلب قديم لا يحتوي travelerStateId. هل يكسر العرض؟

لا، لأن type يدعم travelerCategory القديم ويوجد helper لاستخراج الحالة الفعالة. ده مثال على backward compatibility مع البيانات القديمة بعد تغيير model.

سيناريو: مواطن سجل حضور مرتين لنفس الطلب في نفس اليوم. ماذا يحدث؟

النظام يتحقق من ticket موجود لنفس request/office/date. لو موجود يرجعه بدلاً من إنشاء ticket جديد. ده يمنع تكرار رقم الدور لنفس الطلب في نفس اليوم.

سيناريو: موظف ضغط complete مرتين على نفس ticket. هل يزيد totalCompleted مرتين؟

المنطق يستخدم shouldIncrementTotalCompleted، ولو ticket بالفعل completed لا يزيد الإجمالي مرة أخرى. دي idempotency مهمة لتجنب تضخيم الإحصاءات بسبب ضغطات مكررة.

سيناريو: public API للتوفر رجع أن اليوم متاح، وبعدها submit فشل بسبب الامتلاء. هل ده خطأ؟

لا، ده طبيعي في الأنظمة المتزامنة. availability check لتحسين تجربة المستخدم فقط، لكن الحسم النهائي عند submit على السيرفر. ممكن شخص آخر حجز آخر مكان بين الفحص والإرسال.

سيناريو: عايزين نضيف SMS OTP للمواطنين. تضيفه فين؟

أضيف service مستقل للتحقق من الهاتف، ثم أربطه بإنشاء الطلب أو استرجاع QR. لا أغير model الأساسي كثيراً؛ ممكن أضيف phoneVerifiedAt أو collection مؤقتة للOTP. وأحافظ على rate limiting وexpiry للرمز.

سيناريو: عايزين multi-governorate بدل القاهرة فقط. ما التغييرات؟

أضيف field مثل governorateId في offices والrequests، وأعدل filters والadmin access ليشمل المحافظة. أراجع indexes لأن أغلب الاستعلامات ستحتاج governorateId. وأفصل إعدادات مثل cutoff أو messaging حسب المحافظة إذا اختلفت السياسات.

سيناريو: عايزين الطابور live بدون polling. ما الاختيارات؟

اختيار أول: Firestore realtime listeners لو العميل مسموح يقرأ بيانات محدودة أو من خلال rules دقيقة. اختيار ثاني: SSE أو WebSocket endpoint يبث position. لازم نوازن بين التكلفة، التعقيد، وعدد المستخدمين. polling الحالي أبسط ومناسب لو الدقة كل 20 ثانية مقبولة.

سيناريو: عايز تمنع enumeration لروابط QR. ماذا تفعل؟

النظام بالفعل يستخدم random token، وليس id فقط. أضيف rate limit على pass endpoint إن لم يكن موجوداً، وأجعل response موحد عند فشل token أو id حتى لا تكشف إن الطلب موجود. وأتأكد أن الصفحة noindex ولا تعرض بيانات حساسة.

سيناريو: Firestore query بطيء في صفحة requests. خطة التحسين؟

أفحص query shape والindex المستخدم، أقلل page size، أستخدم cursor pagination بدل offset، أضيف denormalized fields لو فيه joins متكررة، وأقيس عدد reads. كمان أراجع الفلاتر: status/type/office/date لازم تكون مدعومة بفهرس مناسب.

سيناريو: عايزين audit trail لأي تغيير في الطلب. أين تضعه؟

أستخدم activityLogs وأضيف append log عند كل server action/update حساس، مع actor uid وlabel وaction وrequestId وmeta. لا أعتمد على client في كتابة audit log، لأن السجل يجب أن يكون trusted.

طريقة إجابة السؤال المركب: ابدأ بتحديد المشكلة، ثم اذكر الوضع الحالي في المشروع، ثم المخاطر، ثم حل عملي قصير. مثال: "حالياً عندنا count قبل الحفظ، المخاطرة race condition، والحل counter document داخل transaction".

17. سكريبت شرح سريع تحفظه

المشروع عبارة عن منصة Next.js لإدارة خدمات الحجر الصحي بالقاهرة. عندنا واجهة عامة للمواطن فيها معلومات وحجز وشكاوى ومتابعة طلبات، ولوحة إدارة محمية بـ Firebase Auth. الداتا كلها في Firestore، لكن المواطن لا يكتب مباشرة في قاعدة البيانات؛ Server Actions وAPI routes تستخدم Firebase Admin SDK عشان تعمل validation وتحفظ الطلبات بأمان.

أهم flow هو الحجز: المستخدم يختار حالة المسافر والمكتب والتاريخ، النظام يتحقق من cutoff بتوقيت القاهرة، ومن سعة المكتب اليومية، ومن عدم وجود حجز مكرر. بعدها ينشئ request برقم متسلسل وQR pass له token سري. الإدارة تتابع الطلب حسب الأدوار، وموظف المكتب يقدر يحدث الحالة والملاحظات فقط.

فيه كمان نظام طابور يومي: المواطن يسجل حضوره بالطلب أو الهاتف، النظام ينشئ ticket برقم دور داخل transaction، والمواطن يتابع عدد الناس قبله مع دعم تنبيهات PWA. المشروع مهتم بالأمان من خلال Firestore rules، rate limiting، session cookies، وفصل صلاحيات واضح.

لو اتسألت عن نقطة ضعف أو تحسين: ممكن تقول إن الاعتماد على localStorage في "طلباتي" مريح لكنه مرتبط بالجهاز. تحسين مستقبلي ممكن يكون إضافة اختيارية لتسجيل المواطن أو استرجاع QR بطريقة آمنة عبر OTP.
